# Design

## Context

工作区由一个表单处理新建、正文编辑及回复。在写入成功后，浏览器读取工作区上下文来更新评论卡片。元素选择和创建校验共用评论身份查找。归档沿用 `resolved` 状态，以 `resolution` 区分确认解决和历史归档。

## Goals / Non-Goals

新增和编辑立即更新本地评论正文，卡片状态显示后端是否已确认。元素身份继续按现有规则跨版本匹配。进行中讨论的创建和归档讨论的重开共用后端约束，现有批次输入和历史记录继续按原身份读取。

## Decisions

### 1. 在本地列表投影上显示写入状态

新建和编辑立即应用正文，卡片显示待提交并暂不计入待处理。后台失败时保留本地投影和写入标识，卡片提供定位、编辑及重新提交。后台确认后重新计算待处理计数。回复沿用即时显示和原有的失败恢复。

删除、存档和重新打开在请求期间保留原卡片，用相应的禁用操作和文案显示进度。确认后以响应更新卡片和分组，读取失败时保留确认结果。明确拒绝时释放操作锁并恢复卡片操作。后台事件读取通过游标拒绝过时列表。

### 2. 前后端使用同一进行中查找规则

在共享契约中复用精确元素匹配，按现有创建顺序查找最新的非 `resolved` 讨论。画布选择没有匹配时用当前画布目标创建草稿，切到「进行中」并聚焦输入。有匹配时保留待处理原位编辑和其他状态打开卡片的行为。归档列表仍可按评论 ID 查阅多条历史。

在存储事务内检查并创建评论。归档评论显式重开或因回复自动重开时，在同一事务内执行相同检查，发生冲突时在写入线程及更改状态前返回 `comment_exists` 和 `existingCommentId`。这样相邻请求无论先创建还是先重开，都只能产生一条新的进行中讨论。旧数据若已有多条进行中评论，保留每条记录，并以创建顺序最新者为画布默认入口。

### 3. 冲突后由用户决定是否提交到现有讨论

复用工作区已有的冲突提示入口。新建或回复冲突时保留输入，点击入口后才将输入带入进行中讨论的回复表单。显式重开冲突时，入口打开进行中评论卡片。用户提交回复后才写入选定的讨论。服务端继续保护排队或处理中的固定输入，保存评论继续由用户在对话中主动发起下一轮更新。

### 4. 用相同场景对照产品设计稿和运行时

产品设计稿模拟后台延迟和拒绝，运行时使用实际请求。两处对照待提交、重新提交和卡片操作进度，以及归档后新建和重开冲突。

## Risks / Trade-offs

- 列表自动刷新可能重绘卡片。待同步操作独立于卡片 DOM，重绘继续使用本地操作和最新服务端列表。
- 归档回复若先追加线程再校验，会在冲突时留下回复。后端应先检查，调用方收到冲突后由用户决定是否改到进行中讨论。
- 旧客户端仍可能执行跳转归档的选择逻辑。运行时和反馈服务应一起更新，已打开的工作区需要刷新以加载新前端。

## Migration Plan

沿用当前评论、线程、目标和事件结构。既有记录按原 ID 读取，无需数据迁移。若回退应用版本，旧版本继续读取新建和归档的记录，但画布选择及冲突行为会恢复旧规则。
