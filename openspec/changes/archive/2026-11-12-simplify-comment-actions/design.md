# Design

## Context

见 proposal.md。renderComments 当前按 draft、anchor、awaiting_review、resolved 等独立条件追加操作，导致冗余；所有卡片都有新增评论与回复，非 draft 均提供重开，归档在活动批次时禁用。selection 处理排除 resolved，并在匹配多条时选择创建顺序最新的未解决评论。Feedback.add 没有元素唯一校验。

Feedback.edit 的 DELETE 分支同时承担真正删除新记录和 previousDraft 恢复；直接用同一“删除”标签不能准确解释行为。reopen 目前仅阻止 processing，需同时保护 queued。批次 release 也可能产生带批次历史但没有 previousDraft 的 draft，不能误判为可永久删除的新评论。

原版本已在同一画布呈现，但按钮总在锚点存在时显示，return-latest 主要恢复视图，需补齐关联评论的返回定位及草稿保护。设计稿 ui.js 仍有多评论和归档操作，且使用独立模拟状态。主规范明确要求先审核具体设计稿版本；旧测试 review-comments/archive 等也明确依赖将被移除的能力。

## Goals / Non-Goals

**Goals:** 直接展开适用操作，用状态减少冗余；默认单元素讨论；在前后端共同保护历史与固定输入；历史切换不打断讨论。

**Non-Goals:** 不新增折叠菜单、并排对比、弹窗历史浏览或页面级评论；不自动合并/删除旧评论、不跨状态/设备合并，不改 MCP 工具集合或自动消费反馈。

## Decisions

### 1. 先设计稿审核，再同步运行时

先在现有如意设计稿中覆盖所有状态和边界，发布到原产品评审 session，记录待审核 revision 与对照清单。用户批准该具体版本后，才修改工具运行时或抽取会改变运行时的共享实现。复用现有产品审核要求，不把创建变更或测试通过当成设计批准。原批准版本继续作为旧设计记录。

### 2. 集中计算操作，显示顺序固定

批准后将元素身份匹配与操作推导置于可被浏览器、服务层和设计稿按需要复用的纯契约（建议 src/contracts/comment-actions.ts / comment-identity.ts）。状态推导先检查批次 queued/processing，再判断 draft 是否有 previousDraft，以及是否曾出现在批次输入或处理结果中；不只依据 results.length 判定“从未处理”。

| 有效状态 | 基础操作（无锚点时省略定位） |
| --- | --- |
| 新 draft，从未纳入批次 | 定位、编辑、删除 |
| 重开 draft，有 previousDraft | 定位、回复、编辑、撤销重新打开 |
| 其他 draft，有批次历史但无 previousDraft | 定位、回复、编辑 |
| queued/processing 中任何评论 | 定位、回复 |
| submitted / needs_clarification，无活动批次 | 定位、回复 |
| awaiting_review，无活动批次 | 定位、回复、确认解决、重新打开 |
| resolved（confirmed/archived） | 定位、回复、重新打开 |

可对照的元素评论在 target.revisionId 不等于当前已发布 revision.id 时，将查看原版本插在定位后。不为令牌或没有可定位原型入口的对象伪造元素定位按钮。所有适用操作始终可见，窄屏换行，绝不隐藏在“更多”或 hover 内。只有待复核的确认解决为强调操作，删除使用危险文字色。单独的归档/无需处理和新增评论按钮移除；已归档标签、历史 resolution 不变。

### 3. 单元素身份和重复创建保护

身份维度为 kind/objectId/stateId/deviceId/exampleId 加元素锚点，revisionId 不属于身份；双方都有 reviewId 则精确比较该值，否则比较完整 selector。父子元素不匹配，页面中的同组件实例不跨对象合并。无法证明同一元素的无锚点对象不做猜测合并；本轮主要约束元素评论，不改变令牌本身的对象模型。

前端选择包括已解决/归档记录：draft 进入原位编辑，其他状态激活已有卡片和线程但不因打开就改变状态；回复需用户主动选择并保存，才能触发原有自动重开。已存在时不再显示“新增独立评论”或多评论选择。

后端 Feedback.add 在同一 Store.transaction 内验证精确元素身份与插入，重复创建返回明确冲突（建议 comment_exists 与 existingCommentId），不把新正文自动追加到历史或覆盖原文。客户端遇到竞争冲突保留未保存内容，提示并提供已有讨论的入口；不能清空编辑器假装保存成功。没有唯一校验、仅删前端按钮的方案无法防止双标签页重复。

旧重复记录按现有稳定创建顺序（Store.all 按 rowid，更新不改 rowid）选择最新未解决记录，否则选择最新记录作为默认入口。所有旧记录继续在列表保留可读与按状态操作；不重写原锚点、线程、结果或快照，不做数据库清理/合并。默认选取规则前后端一致，不新增记录。

### 4. 删除和撤销重开分离

真正 DELETE 仅允许新 draft，且无任何既有批次引用、结果与 previousDraft。对有历史记录的 DELETE 返回明确拒绝，不再以“删除”偷偷恢复状态。

增加明确的撤销重开操作（建议现有 HTTP review action 扩展 cancel_reopen；不增加 MCP 工具）：仅允许无活动批次且具备 previousDraft 的 draft，恢复保存的正文/状态并清理恢复标记，保留已保存线程、结果、resolution 和原定位。queued 与 processing 均拒绝编辑、删除、重开和撤销重开，UI 与服务端规则一致。旧 archive API 可为兼容保留其保护条件，但卡片不再提供入口，不能把历史 archived 转为 confirmed。

### 5. 原版本展示与返回定位

继续复用 historicalRevision 与不可变快照。在画布顶部固定显示“正在查看评论原版本 · 只读”与“返回最新版本”，右侧讨论保持，未保存正文/回复不丢失。只读针对历史画布，不阻止按当前状态操作既有讨论；历史画布不可新建元素评论。

记录当前对照 commentId，返回最新版本时重新读取其目标与最新删除位置，再调用既有定位路径。若在查看历史期间又发布新版本，则返回最新活动 revision；无法匹配组合/锚点时明确提示，不能自动漂移到其他元素，也不能用历史坐标冒充成功。不以历史切换触发重开、解决或发布，不重建评审 session。

## Risks / Trade-offs

- 隐藏按钮但接口仍能改固定输入 → 服务端同时执行状态与批次历史检查，补充直接请求反例。
- 旧重复记录损失历史或选取漂移 → 保留原记录，复用稳定创建顺序，测试编辑/重启后默认入口一致。
- 取消重开误删追加内容 → 明确只恢复正文与状态，已保存线程不删。
- 当前设计稿审批与工具实现脱节 → 同一状态矩阵验收设计稿和运行时，记录批准 revision 和有理由保留的差异。

## Migration Plan

先完成设计稿审核，再实施共享契约与服务端保护、浏览器行为，最后同步测试及文档。无需数据库版本提升；旧记录只读取、不批量改写。更新当前主规范时移除旧多评论和独立手动归档要求，以新契约替代。旧历史查看和已有归档 API 的数据仍有效；回滚工具不应破坏新增记录。升级旧工作区需要刷新外壳、客户端重启后端，不在本变更中自动操纵客户端进程或发布 npm。
